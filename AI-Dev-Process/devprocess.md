# Development Process

## Process Definition

1. Prompt Spec: Describe the intention and define mocks (store any artifacts in the `spec/` folder if needed).
2. Grill me -> Requirements Specification (use `grill-me`, then `to-prd`): Stress-test the idea and generate a requirements specification (`PRD.md`).
3. Derive Issues/Stories (use `to-issues`): Extract issues/stories and, where project policy permits, store them in `issues/needs-triage` or create GitHub issues initially marked as `needs-triage`. If issue creation is owned by someone else, record candidates for that owner instead.
4. Select Core Stories: Choose key stories for prototyping.
5. Architecture Definition (use `grill-me`): Define the architecture and folder/package structure (store in `design.md`).
6. Incremental Implementation & Workflow Management (use `triage`): Triage issues first and route them to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. Once an issue is ready-for-agent, move it into the implementation flow, e.g. `todo -> in-progress -> review -> done`.
   - Use SDD (Specification-Driven Development): Before TDD, explicitly inspect `design.md`, cross-check the planned issue-level design against it, and decide whether issue-level specification and Mermaid diagrams would add value. If they do, recommend that step first, name the diagram types and why they help, and—if the user agrees—use the Mermaid skill to add them inline to the issue markdown file by default. Do not create those diagrams without this consistency check first. Keep them consistent with `design.md`, and if the cross-check finds any inconsistency, omission, or architectural drift, raise the inconsistency explicitly and either update `design.md` now or create follow-up design work if the inconsistency is deferred.
   - Use TDD (Test-Driven Development) (use `tdd`): Implement the stories using TDD.
   - Maintain Design: If difficulties arise or refactoring leads to design changes, update `design.md` accordingly.

## Project Overrides

Three of the in-repo skills carry behaviours that **conflict with this project's policies**. The overrides below are authoritative: when an in-repo skill's instructions and the overrides below disagree, **the overrides win**. The same overrides are mirrored in a short header block at the top of each affected `SKILL.md` so the agent sees them regardless of entry point.

### Skill `to-prd` — adapted

- **Do not push to the GitHub issue tracker.** The skill's own instructions say *"publish it to the project issue tracker. Apply the `ready-for-agent` triage label"*. **Ignored here.** Issue authorship is owned by the team per the wiki Definition of Done (PO writes feature / story issues; team members file bug issues; the agent does **not** create or label issues).
- **Use [`PRD-TEMPLATE.md`](PRD-TEMPLATE.md), not the skill's built-in template.** The built-in `Problem / Solution / User Stories / Implementation Decisions / Testing Decisions / Out of Scope / Further Notes` shape does **not** match the project's PRD structure (Product Summary / Backlog Structure / Team Conventions / Problem Statement / Goals / Non-Goals / Existing Features / Missing or Incomplete Features / FR{n} / NFR{n} / Acceptance Criteria / Risks and Assumptions). `PRD-TEMPLATE.md` documents the project-canonical shape and is the single source of truth for how a PRD looks here.
- **Write target:** the project-level PRD lives at [`PRD.md`](PRD.md). Per-feature PRDs (when Inkrement 3 starts) may land under [`prds/`](prds/), one Markdown file per Lastenheft §3.3 item, using the same template (dropping sections that don't apply at the feature level).
- **Domain glossary:** [`AI-Dev-Process/glossary.md`](glossary.md) is the dedicated source — DE↔EN mappings between Lastenheft / wiki terms and code identifiers. The Lastenheft and [`../spec/class_diagram.md`](../spec/class_diagram.md) remain the canonical authorities for any term not yet in the glossary; the glossary itself is derived from them and updated as new terms surface. The skill's *"use the project's domain glossary vocabulary"* line resolves to `glossary.md` first.

### Skill `triage` — read-only

- **Do not post comments to the GitHub issue tracker, do not apply or change labels, do not close issues.** The skill's own header says *"Every comment or issue posted to the issue tracker during triage must start with this disclaimer"* — that workflow is **not used** in this project.
- **Output recommendations only.** Surface category (`bug` / `enhancement`) and state (`needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`) suggestions to the developer in chat, together with the reasoning, the codebase summary, and (for bugs) the reproduction attempt. The team applies labels and posts comments themselves.
- **`/grill-with-docs` invocation** is also read-only: ask the developer the grilling questions and capture answers in chat (or in `devprocess.md` if a record is wanted), do not post grilled output as a triage-notes comment.
- **`.out-of-scope/` knowledge base is not used** in this project. If a wontfix-enhancement rationale should be remembered, record it in [`WORKFLOW-LOG.md`](WORKFLOW-LOG.md) (as a project-state log entry) or in this `devprocess.md` → "OPEN_QUESTIONS" (if still being decided) instead.
- **Agent-brief drafting (`AGENT-BRIEF.md` rules) is still useful** — when the developer asks the agent to draft a brief for an already-`ready-for-agent` issue, follow the durability / behavioural / acceptance-criteria rules; deliver the draft in chat for the developer to paste themselves.

### Skill `grill-with-docs` — adapted

The `grill-with-docs` skill ([`Skills/grill-with-docs/SKILL.md`](Skills/grill-with-docs/SKILL.md)) is the variant of `grill-me` that *"sharpens terminology and updates documentation (CONTEXT.md, ADRs) inline as decisions crystallise"*. Several of its assumptions do not hold here:

- **Glossary file location.** The skill expects [`CONTEXT.md`](Skills/grill-with-docs/CONTEXT-FORMAT.md) at the **repo root** and auto-creates one if it does not find it. **Do NOT create `CONTEXT.md` at the repo root.** The project glossary lives at [`AI-Dev-Process/glossary.md`](glossary.md). When the skill instruction says *"Update CONTEXT.md inline"* or *"Challenge against the glossary"*, read both as referring to `AI-Dev-Process/glossary.md` instead. Update the glossary by editing that file directly (and only that file).
- **`CONTEXT-MAP.md` multi-context layout.** The skill mentions a `CONTEXT-MAP.md` for repos with multiple bounded contexts. This project has **one bounded context** (the road-network domain). Do not create `CONTEXT-MAP.md`.
- **ADRs.** Covered by "ADRs across skills" above. `docs/adr/` is **not used**; ADR-worthy findings surface in chat for the team to record in `design.md` or the wiki.
- **Read-only triage interaction.** When the skill is invoked from within `triage/SKILL.md` (which is itself read-only per the `triage` override), grilling questions go to the developer in chat — no tracker comments, no triage-notes posts.
- **Inline glossary edits during a session.** The skill's *"Update CONTEXT.md right there. Don't batch these up"* rule is honoured against `AI-Dev-Process/glossary.md`. When the developer settles a new term during grilling, add the row to the matching table in `glossary.md` immediately (follow the "How to extend this glossary" rules in that file's footer).

### Skill `to-issues` — disabled

- **Do not invoke at all.** Issue creation is owned by the team per the wiki Definition of Done (PO drives feature / story issues; bug issues are filed by team members). The skill is committed in `Skills/to-issues/` only so the repository stays a complete reference bundle.
- If the workflow ever reaches a point where deriving issues from a plan would be useful (e.g. an Inkrement-3 kick-off), surface the candidate issue list to the **developer / PO** in chat. They decide whether to file them.

### ADRs across skills

**There are no ADRs in this project.** Several skills (`tdd`, `grill-with-docs`, `to-prd`, `to-issues`, `triage`) reference ADRs — either to *"respect ADRs in the area you're touching"* or to look for / create entries under `docs/adr/`. None of those expectations are met by the repository today, and that is **intentional**:

- Architecture decisions are recorded in [`design.md`](design.md) (the "Intended Architecture Direction" and "Known Design Issues" sections).
- Team-level decisions are recorded in the [team wiki](https://github.com/sekassel/STP-2026-Team-D.wiki.git), page `Gemeinsame-Grundlagen.md`.
- Process / workflow decisions are recorded in [`WORKFLOW-LOG.md`](WORKFLOW-LOG.md) (project-state diary) and in this `devprocess.md` → "Project Overrides" (when they create a new rule).

When any skill looks for ADRs, the agent treats `design.md` + the wiki + this file as the substitute. **Do not create a `docs/adr/` folder or ADR files** unless the team explicitly decides to start formal ADRs — in which case the convention is open (`docs/adr/` at the repo root would be the natural location), the decision goes into a [`WORKFLOW-LOG.md`](WORKFLOW-LOG.md) entry (and optionally a [`CHANGELOG.md`](CHANGELOG.md) entry if `docs/adr/` itself is created as a structural change), and this subsection is updated.

Specific consequences for the affected skills:

- **`tdd`** — *"respect ADRs in the area you're touching"* resolves to `design.md` + wiki.
- **`grill-with-docs`** — *"Offer ADRs sparingly"* / the auto-create-`docs/adr/` workflow is **off**; the skill stays read-only and surfaces ADR-worthy decisions in chat for the team to record manually in `design.md` or the wiki instead.

### Setup data normally provided by `/setup-matt-pocock-skills`

The three skills above reference `/setup-matt-pocock-skills` for issue-tracker configuration and triage-label vocabulary. That command is not committed in this repo. The substitute is **this `devprocess.md`**:

- **Issue tracker:** GitHub, repository `sekassel/STP-2026-Team-D` (see "Project Layout" → "External authoritative sources").
- **Triage label vocabulary in use:** GitHub labels mirror the canonical roles (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`, `bug`, `enhancement`) plus the project-specific `epic`, `optional`. The wiki / PO is authoritative if the GitHub label set diverges.
- **AFK / HITL convention:** all agent work is HITL (human-in-the-loop) by default in this project — the developer reviews every change before it lands on `dev`. The skill's `AFK` / `HITL` slice distinction is read as "HITL = requires PO design call before implementation; AFK = the developer can drive it through TDD with the agent".
